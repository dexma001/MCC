# AI_Streaming — 실시간 보정 런타임 + Warudo(VMC) 브리지

`checkpoints/`의 학습된 모델을 **한 프레임씩 들어오고 나가는 형태**로 감싼 배포 런타임과, 트래커와
**Steam Warudo** 사이에서 VMC 를 실제로 송수신하는 브리지다. `AI_model/` 의 파일은 수정하지 않고 import 해서 쓴다.

사용법(옵션·상태 HTTP·문제 해결)은 `USAGE.md`. 이 문서는 동작 원리와 실측이다.

## 파일

| 파일 | 역할 |
|---|---|
| `vmc_bridge.py` | **서비스 진입점**: 트래커(VMC) → 보정 → Warudo(VMC). 콘솔 통계·프레임 로그·상태 HTTP, 자체 점검 `--loopback-test`(합성 관통 모션) |
| `server.py` | **상시 실행 supervisor** — 브리지를 자식으로 띄워 크래시·멈춤 시 재시작, 회전 로그, 중복 실행 방지, 원격 상태·제어 |
| `server_config.json` | 서버 설정 (체크포인트 에폭 고정, 포트, torch 스레드 수, 출력 지연, 감시 주기) |
| `start_server.bat` | 서버 실행 배치 (더블클릭 / 작업 스케줄러용) |
| `control.py` | 브리지의 로컬 상태·제어 HTTP (`/health` `/status` `POST /bypass /reset /shutdown`) + 클라이언트 |
| `corrector.py` | **보정기 본체** `StreamingCorrector.push(frame) -> (frame, info)` |
| `retarget.py` + `rig_tpose.json` | **리그 로컬 ↔ VRM 정규화 로컬 변환** (Warudo 호환의 핵심, 아래 참조) |
| `contract.py` | 87차원 입출력 규약 — 관절 순서·쿼터니언 규약·단위·프레임 검사 |
| `sinks.py` | VMC 번들 생성·송신 (`VmcOscSink`) |
| `paths.py` | 경로 부트스트랩 (`AI_model/` 을 sys.path 에 얹고, 체크포인트·뼈대 오프셋 절대 경로 제공) |
| `USAGE.md` | **사용법 상세** |

## 파이프라인

```
트래커(VMC) → [VRM→리그 변환 + 세션 정규화] → 보정 → [정규화 되돌림 + 리그→VRM 변환] → Warudo(VMC)
               손가락·표정·눈·UpperChest 는 그대로 통과 ───────────────────────────────▶

보정 = 입력 프레임 → [30프레임 링버퍼] → 모델 → 저역통과 → 사영 → 출력 프레임
                       └ 버퍼가 찰 때까지(29프레임, 약 1초) 원본 그대로 통과
```

- 순서는 강제다. 필터를 사영 뒤에 두면 관통이 되살아난다(실측: 필터→사영 0.000cm vs 사영→필터 1.276cm).
- **출력 자리**: 윈도우 끝에서 `emit_lag`(기본 2) 프레임 앞을 내보낸다 → 출력은 입력보다 2프레임(67ms) 늦다.
  끝자리는 미래 문맥이 없어 윈도우마다 답이 달라지고, 그것이 보정 아바타의 튐으로 보였다(아래 실측).
- **hold 틱**: 브리지는 자기 30fps 시계로 돈다. 트래커가 더 빠르면 최신 프레임만 쓰고(sample-and-hold, 보간 없음),
  새 프레임이 없는 틱은 모델에 넣지도 보내지도 않는다(Warudo 는 마지막 포즈 유지). 그 사이 온 표정·손가락은
  직전 출력 포즈에 실어 보낸다.

## Warudo 호환

### 1. 쿼터니언 규약 변환

Warudo 의 VMC 수신은 **"T-포즈에서 모든 본의 로컬 회전이 (0,0,0)" 인 정규화 모델(VRM)** 을 전제한다.
모델이 학습한 87차원 텐서의 쿼터니언은 그 규약이 아니다(원본 FBX 리그의 로컬 회전 — 정지 자세에서
Spine ≈ Y축 90°, UpperLeg ≈ Z축 180°). 변환 없이 보내면 아바타가 완전히 뒤틀리고, 트래커의 VRM 값을 그대로
모델에 넣으면 학습 분포 밖의 입력이 된다.

`retarget.py` 가 양방향 변환을 한다: `V_b = G0_parent · L_b · inv(G0_b)`. **모든 관절의 월드 위치를 정확히 보존**하고
(최대 오차 0.00008cm), 각 본의 월드 회전이 독립이라 오차가 사슬을 따라 누적되지 않는다. `G0`(리그 T-포즈)는
`rig_tpose.json` 에 들어 있다.

**남는 자유도**: 뼈 축 둘레의 비틀림(롤)은 기하가 결정하지 못한다. 위치는 맞지만 손바닥 방향·팔 롤·발 기울기가
아바타와 다를 수 있다 → Warudo 에서 눈으로 확인한다.

### 2. 세션 정규화

학습 데이터는 파일마다 첫 프레임의 앞 방향을 정면으로 돌리고 Hips 위치를 첫 프레임 기준 상대값으로 둔 것이다.
`vmc_bridge.SessionNormalizer` 가 라이브에서 같은 규약을 재현한다(첫 프레임 Hips 원점화 + 다리 위치로 잰 앞 방향을
+Z 로). 모델 입력에만 적용하고 출력에서 되돌리므로 Warudo 는 트래커의 절대 위치·방향을 그대로 받는다.

### 3. VMC 패킷 (Warudo 기본 포트 39539)

프레임당 OSC 번들 1개: `/VMC/Ext/OK 1 3 0 1` → `/VMC/Ext/Root/Pos` → `/VMC/Ext/Bone/Pos` × 21
(**Hips 만 위치**, 나머지 위치 0) → pass-through → `/VMC/Ext/T`. 본 이름 21개는 전부 Unity HumanBodyBones 철자.
UpperChest 는 리그에 없다 — 트래커가 보내면 Chest 에 접어 모델에 넣고, 출력에서 다시 풀어 원본 UpperChest 를 통과시킨다.

### 4. 배선

* Warudo: 캐릭터 → 모션 캡처 → **VMC** 수신, 포트 39539, **VRM 모델**(정규화 본) 사용.
  모델은 T-포즈에서 본 회전 0 이어야 하며, 옛 VRM 은 Enforce T-Pose 로 재출력.
* 트래커(VMC 앱·VSeeFace·mocopi 등)의 송신 대상을 Warudo 가 아니라 **브리지의 `--listen-port`(39540)** 로.
  트래커가 Warudo 로 직접 보내면서 브리지도 보내면 두 스트림이 겹쳐 아바타가 떤다.
* Warudo 의 **VMC Sender** 를 입력으로 쓰면서 같은 캐릭터가 VMC 수신도 하면 보정값이 다시 입력되는
  **되먹임 고리**가 된다. 입력·출력 캐릭터를 분리하거나 외부 트래커를 쓴다.
* 처음에는 보정 캐릭터 옆에 트래커 원본을 직접 받는 캐릭터를 하나 더 두고(다른 포트) 나란히 비교하면
  팔 롤·손바닥·발 기울기·골반 높이·지연을 눈으로 확인하기 쉽다.

## 동작 규칙

* 트래커 수신이 0.5초 없으면 송신을 멈춘다(Warudo 는 마지막 포즈 유지).
* 2초 이상 끊겼다 돌아오면 세션(정규화 기준·링버퍼)을 리셋한다 → 재개 첫 1초는 원본 통과.
* 보정 예외는 원본 통과로 흡수한다(방송이 죽지 않는다). `b` 키 / `server.py --bypass on` 으로 보정 끄기.
* 트래커 fps ≠ 30 이면 sample-and-hold 로만 맞춘다(보간 없음). 60fps 트래커는 절반을 버리고,
  30fps 보다 느리면 새 프레임이 있는 틱에만 보정·송신한다.
* Hips 절대 높이는 트래커 값을 그대로 쓴다.
* 아바타 신장 차이는 ±15% 까지 관통 판정에 무해(실측). 극단 체형은 미측정.
* **체크포인트 에폭**: `vmc_bridge.py` 를 직접 실행하면 checkpoints 폴더의 가중치를 선택한다.
## 실측

### 보정 품질·지연 (`l10.1_phys0.5` epoch 4000, CPU, held-out 8파일 600프레임, 2026-10-03)

개발 환경에서 데이터셋을 실시간처럼 흘려 잰 값이다(emit_lag 0 시점 측정).

| 시나리오 | 지연 p50/p95/max (ms) | 예산(33ms) 초과 | 보정 프레임의 4쌍 관통 | 입력 대비 이동 (전신/손) |
|---|---|---|---|---|
| clean (손상 없음) | 5.6 / 9.2 / 23.7 | 0.00% | 0.000 cm | **1.58 / 1.38 cm** |
| transient (잠깐 관통) | 6.7 / 8.1 / 19.9 | 0.00% | 0.000 cm | 1.75 / 2.00 cm |
| persistent (계속 관통) | 5.8 / 14.1 / 20.5 | 0.00% | **0.000 cm** (입력 max 8.54) | 2.54 / 10.82 cm |
| legacy80 (학습 분포 밖) | 5.5 / 6.8 / 13.0 | 0.00% | 0.000 cm (입력 max 7.72) | 4.16 / **23.58 cm** |

- clean 의 이동량이 do-no-harm 지표다. 0 이 아니다 — 멀쩡한 입력도 평균 1.6cm 움직인다.
- legacy80 에서 손이 23.6cm 움직이는 것은 교정이 아니라 동작 삭제에 가깝다(재학습 영역).
- 지연은 실행마다 흔들린다. 상시 실행(torch 스레드 1, Warudo 와 CPU 공유 가정)에서는 p95 약 20ms (USAGE.md §2 실측).

### 보정 아바타 튐 (2026-10-07, 실제 방송 경로)

가상 트래커(persistent 손상) → UDP → 브리지(`server.py` 와 같은 명령줄) → 수신기, 60초.
중간점 이탈 = |P_t − (P_t−1 + P_t+1)/2| 의 관절 최대(cm). 이웃 프레임과 어긋나 튀어 보이는 정도다.

| 조건 | 보정 출력 p99 | 보정 출력 >6cm /1000프레임 | 원본 >6cm | 손상 입력 >6cm |
|---|---:|---:|---:|---:|
| 30fps, 수정 전 → 후 | 15.2 → **9.7** | 48 → **25** | 4 | 36 |
| 25fps, 수정 전 → 후 | 15.2 → **9.1** | 46 → **22** | 3 | 42 |
| 손상 없는 입력 30fps, 수정 전 → 후 | 13.5 → **9.7** | 35 → **23** | 4 | 4 |

- 개선은 거의 전부 `emit_lag` 2 몫이다. CPU 부하(프로세스 8개)를 걸어도 같았다.
- 손상 없는 입력에서도 보정 출력의 큰 튐이 원본의 약 6배 남는다(모델 재학습 영역).
  시작·리셋 직후 1초 뒤의 전환 팝 1회도 그대로다.
- 되돌리기: `server_config.json` 의 `"emit_lag": 0`(지연 최소, 튐 큼), `"hold_repush": true`(2026-10-07 이전 hold 동작).

## 남아 있는 한계 (런타임에서 해결 불가)

- do-no-harm 이 0 이 아님 (clean 1.58cm, 큰 튐 원본의 약 6배 — 재학습/손실 설계 문제)
- 보장 대상은 학습된 4쌍(왼·오른 아래팔↔몸통, 아래팔↔아래팔, 정강이↔정강이). 그 밖의 전신 관통 4~6cm 잔존(2026-09 측정, epoch 4000 미재측정)
- 지연 상한의 **보장** 없음 (예산 가드가 사영 반복을 깎지만, 사영 비용은 입력 의존)
- 프리즈/텔레포트/트래커 소실은 학습에서 본 적이 없는 손상 유형
- 리그 T-포즈의 뼈축 비틀림(롤)은 기하로 확정 불가 — Warudo 에서 눈으로 확인
- 60fps 이상 트래커는 실측하지 못했다(가상 트래커가 고fps 에서 재생 속도까지 빨라져 검증 불가)
